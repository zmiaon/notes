# 写笔记规范

> 这份规范基于对现有 45 篇笔记的实际检查得出，不是通用建议。写新笔记前对照一遍即可。

## 一、三个根因

具体毛病（空壳、上色、截图、重复版本）背后是三个错位。

### 1. 目标错位：为"好看"写，不为"下次能用"写

`addEventListener 绑定事件.md` 里的 `<span style="color:rgb(255,0,0)">`、`箭头函数.md` 里的 `<mark class="hltr-red">`，都是上色插件生成的 HTML。写的时候要决策配什么颜色，改的时候要改标签，迁移到知识库或 GitHub 就变成源码。

好看的成本是持续的，收益是一次性的，而且经常和好用冲突。

### 2. 内容错位：抄"是什么"，缺"为什么"和"坑"

| 内容 | 实际价值 |
|---|---|
| `导入导出.md` 的 `require` / `import` 写法 | 低，官网第一页就有 |
| 同篇的「ESM 要加 `type: module`」 | 高，这是真会卡住的地方 |
| `Python相关知识点.md` 的「引入」两个字 | 零，只记了"我准备学" |
| `2026年7月21` 的 MySQL CRUD 四段示例 | 低，差异只有一个返回值结构 |

官网写"怎么用"，笔记该写"你为什么这么选、哪里会炸"。

### 3. 结构错位：每一篇都在现场做决策

没有模板，每次写都要想：要不要换行、要不要分节、加不加颜色、举不举例子。这部分消耗的精力比写内容本身还多。加上没有索引和版本管理，写完就沉底。

## 二、四条原则

1. **笔记是检索工具，不是作品。** 判断标准只有一个：三个月后能不能在 10 秒内找到并看懂。
2. **只记三样：判断、坑、链接。** 能查到的不抄，抄了会过期。
3. **一篇只解决一个问题，标题写成问题。** `LangChain知识点` 这种标题，三天后自己都不知道里面有什么。
4. **格式只服务于扫读。** 标题、列表、加粗、代码块、表格，五种足够。颜色不增加信息，只增加维护成本。

## 三、写笔记的流程

捕获 → 判断 → 成稿 → 归档 → 复习

### 第 0 步：捕获（不排版）

学习过程中随手记到当天草稿里，只记关键词和疑问。不边学边排版，排版留到成稿阶段。

### 第 1 步：判断值不值得写成笔记

1. **30 秒内能搜到权威答案吗？** 能 → 不写，或用完就走
2. **我上次因为它卡了超过 10 分钟吗？** 是 → 必写
3. **这条信息一年后还成立吗？** 变化快 → 只记链接

三个都答"不值得"，直接删草稿，不用有负罪感。

### 第 2 步：套模板成稿

写完自检一遍：能不能删掉一半？删掉后读不懂，才留下。

### 第 3 步：归档

- **命名**：`主题-问题或结论.md`，例如 `Node-ESM怎么启用.md`
- **位置**：跨项目可复用的知识进 vault；随代码变化的记录留在项目仓库
- **入口**：在 `00-索引.md` 对应分组加一行「链接 — 一句话说明」
- **版本**：交给 obsidian-git 自动提交

### 第 4 步：复习

不要"重读笔记"，而是带着问题去搜。搜到了、看懂了就关掉。自测题答不上来，才往下看坑点。笔记的价值在"被命中"，不在"被通读"。

## 四、记什么，不记什么

### 应该记

| 类型 | 例子 |
|---|---|
| 选择依据 | 这个项目为什么用 ESM 不用 CommonJS |
| 坑与报错原文 | `Cannot use import statement outside a module` 的原因和改法 |
| 项目约定 | 这个仓库的目录规范、接口命名规则 |
| 心智模型 | 用自己的话解释「ref 为什么模板里不用 .value」 |
| 高频命令速查 | `个人记录/常用指令.md` 这种表 |
| 跨环境差异 | 两台电脑、不同 Node 版本下的行为差异 |

### 不该记

| 类型 | 原因 | 替代做法 |
|---|---|---|
| 官方文档里的语法 / API | 一定查得到，还会过时 | 收藏链接 |
| 大段 AI 生成的教程 | 读一遍很爽，第二遍全是噪音 | 只留结论和坑 |
| 以截图为主体的内容 | 图丢了知识就没了，还搜不到 | 用文字，可选配图 |
| 一次性的过程记录 | 只对当天有用 | 放日记，不进知识库 |
| 版本相关的具体结论 | 明年就是错的 | 记链接，不记结论 |

### 一个例外

系统性学习的课程笔记（C 语言、Vue3 那类）可以保留教材式的完整度，因为目标是建立体系，不是快速检索。用轻量模板反而会把知识切碎。

区分方法：查漏补缺用轻量模板，系统学习用结构化提纲。两套并存，不要互相迁就。

## 五、笔记模板

```markdown
# 一句话说清这篇解决什么问题

**结论**：先给答案，3 行以内

**触发场景**：什么情况下我会需要它
-
-

**最小示例**：能直接跑的代码，最多两段

**坑**：报错原文 + 原因 + 怎么绕过去

**官方链接**：权威出处（会过期的内容只记这里）

**自测**：1–3 个 Q，只留容易忘、容易混的
```

## 六、维护机制

- **每月一次，30 分钟**：删空壳、合并重复、补索引、检查断链
- **同一内容查了三次以上**：不要写成笔记，做成代码片段或模板
- **同一主题出现三个版本**：立刻合并，旧版删掉
